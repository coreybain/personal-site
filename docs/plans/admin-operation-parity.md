# Administration operation parity

Source audit: 17 September 2026, starting from personal-site `737affea460647dbcb7861bef2a290bc936e0894`. This is the baseline for the [MCP and native iOS migration](mcp-native-ios-admin-migration.md). Concurrent implementation changes must be assessed separately against this baseline.

This inventory establishes source-level coverage only. It does not establish that a screen has been exercised on a simulator or device, that deployed data matches local source, or that a planned MCP operation is implemented. The first implementation slice is scoped to management authorization, reads and a staged post workflow. Remaining write families, upload migration, native redesign and admin deletion are later work.

## How to read the matrix

- **Present:** the native control and model call exist in source. Runtime acceptance remains open.
- **Partial:** some fields or workflow behavior differ from the browser.
- **Missing:** no matching control was found in the audited native files.
- **Live:** saving modifies the published source immediately; page caches or derived indexes can lag.
- **Draft row:** an unpublished record is hidden, but this is not a separate revision of an already-published record.

Paths in the tables are repository-relative. Browser editor paths below `apps/web/src/app/admin/(shell)/` are abbreviated to `admin/`; native feature paths below `apps/ios/Home/Features/` are abbreviated to `ios/`. Backend operations are in `packages/convex/convex/<module>.ts`. All native model calls are in `apps/ios/Home/Backend/HomeAppModel.swift` unless noted.

## Concurrency and publication findings

The baseline `lib/revision.ts` treats missing revisions as zero and rejects a mismatch only when the caller supplies an expectation. Browser forms and native editors generally capture and send revisions, but the legacy endpoint contracts permit omission. New machine writes must require expectations independently of that legacy compatibility.

| Operation family | Baseline revision behavior | Baseline publication behavior |
| --- | --- | --- |
| `projects:update/publish/unpublish/setFeatured/remove` | Optional `expectedRevision`; successful changes advance revision | Updates to published rows are live. Media replacement rechecks sanitisation. No separately staged revision exists. |
| `labs:update/publish/unpublish/setFeatured/remove` | Optional `expectedRevision` | Updates to published rows are live. No separate staged revision. |
| `posts:update/publish/unpublish/remove` | Optional `expectedRevision` | Updates to published rows are live and can schedule immediate knowledge reindex. A separate staged-post contract is necessary for the MCP workflow. |
| `projects:setSortOrder`, `labs:setSortOrder` | Required revision array, duplicate detection, exact full-row membership check, single transaction | Live ordering changes; published filtering still applies. |
| `experienceEntries:update/setSortOrder/remove` | Optional expectation; swap has optional first/second expectations | Every write can synchronously rebuild the live résumé experience and advance its revision. |
| `resume:upsert/syncFromEntries/remove` | Optional expectation | Live singleton; no publish step. Upsert rebuilds experience from source entries. |
| `siteSettings:upsert/setAvailability/remove` | Optional expectation | Live singleton; identity updates also refresh snapshot identity. |
| `funEntries:update/remove` | Optional expectation | Entries are always public; create/update/remove refresh the latest-fun snapshot. |
| `contactMessages:setStatus/remove` | No revision fields/checks | Private triage update or permanent deletion. Archive is one status, not a deletion. |
| `ingestTokens:issue/revoke` | No editorial revision; revoke is idempotent | Private credentials. Revocation takes effect through token verification, independent of content publishing. |
| Legacy creates across content families | No caller idempotency key/receipt contract | Retrying a create after losing the response can fail slug uniqueness or create a duplicate for entities without slugs. |

The baseline has no general mutation receipt/audit-log contract. Existing no-op behavior, a unique slug and Convex transactional execution are not substitutes for application retry idempotency. A first management slice may add receipts only to its own operations; it must not imply all legacy workflows now have them.

Nested `links`, media, capabilities, education and settings blocks are often replaced whole. Future partial tools must fetch/merge against the expected revision or expose full replacement explicitly. Omission means preserve for patch APIs; nullable fields may mean clear. Do not translate omitted tool fields into empty arrays or nulls automatically.

Deletes in projects, Labs, posts, Fun and experience are hard deletes. Uploaded files are generally left in storage; the current source does not implement the cleanup its UI anticipates. Unpublish exists only for projects/Labs/posts. Do not label delete as archive or promise undo.

## Public consumers and code-owned exceptions

1. `apps/web/src/lib/data.ts` uses an anonymous `ConvexHttpClient` for published projects/Labs/posts, `resume:get`, `siteSettings:get`, Fun and snapshot reads. Preserve that anonymity; an owner credential in this path would make identity-sensitive post reads include drafts. Site pages commonly revalidate at 300 seconds, so a saved mutation receipt is not proof of an already-refreshed public page.
2. `apps/web/src/app/(site)/resume/page.tsx` and `apps/web/src/app/api/resume.pdf/route.ts` share the selected-project constants and SpiritDevs override described above. `packages/pdf/src/ResumePdf.tsx` is a renderer; schema migration must update both public props and Swift decoding, not only its layout.
3. `apps/web/src/lib/labsCatalog.ts` makes Pathway first, supplies `PATHWAY_LAB` when the public data lacks it, and removes `statline`. As a result, unpublishing or deleting the backend Pathway row can still display the hard-coded fallback. Migrate this rule deliberately before claiming backend publication is authoritative for all Labs. Keep the currently approved editorial selection during that migration.
4. `apps/web/src/app/(site)/page.tsx` excludes `soldonline` from homepage projects and matching AI attribution; other pages can still show it. Preserve the homepage-only omission, section ordering and existing curated ordering. This is not a backend deletion request.
5. Projects/Labs/posts schedule `knowledge:indexSource` on relevant live edits/publication and knowledge removal or publication changes when appropriate. `resume.ts` contains commented proposed résumé indexing hooks rather than active scheduling. Updating the résumé alone does not prove Ask's embedded résumé content refreshed. Test or explicitly run the approved rebuild when that guarantee is needed.
6. Public Ask remains `apps/web/src/app/api/ask/route.ts` calling `ask:checkRateLimit` and `ask:retrieve`. Preserve the AI SDK, retrieval source filtering, streaming route and anonymous abuse controls when browser auth is removed.
7. Public contact submission remains `apps/web/src/app/(site)/contact/actions.ts`, calling `contactMessages:submit` and `finishAttachments`. It verifies BotID and uploads attachments directly with `UTApi`; it does **not** depend on the admin file router. Removing `uploadthing` or `UPLOADTHING_TOKEN` wholesale would break this public feature even after native uploads move.
8. `packages/convex/convex/http.ts`, `ingest.ts`, `ingestTokens.ts`, `crons.ts` and snapshot builders serve collector/HealthKit ingestion and scheduled aggregation. Preserve their independent credential scopes and routes.

## Required evidence by milestone

The first stdio MCP milestone can be accepted without declaring full migration complete: its test record must cover the implemented scopes, operation schemas, transactional authorization, response receipts, public draft exclusion and a real supported-client connection. Remaining matrix rows stay open.

Before the final admin removal, attach source and runtime evidence for each required row, noting the environment and release. The new staged post path must coexist safely with legacy browser/native writes during the transition: a concurrent legacy edit must result in a conflict rather than being overwritten by publication of an old staged version. Equivalent tests remain necessary when project and Lab staging are introduced.
